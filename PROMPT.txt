设计院那边有位同事在给我们这套反渗透核算接口做录入表单，他们的表单规矩是：没填的框不往请求里带，填了 0 的框就老老实实带一个 0。上周他转来两条请求，说结果跟他想的不一样，我自己照着打了一遍，确实不对。

这两条请求只差一个数。进料都是 5 g/L、摩尔质量 58.44 g/mol、298.15 K、因子 2，工作压差 12 bar、进料 1000 L/h、渗透系数 1.8、膜面积 36 m²、截留率 1。第一条另外写了摩尔浓度 0.05 mol/L，服务回 400、code 是 inconsistent_concentration，这没毛病，5 除以 58.44 大约 0.0856，和 0.05 对不上。第二条把摩尔浓度写成 0，按说离得更远，服务却回了 200，拿 0.0856 mol/L 一路算出 4.24 bar 的渗透压和整套回收、浓水结果，好像那个 0 从来没出现过。用户在表单上填了 0，可能是手滑，也可能是想说纯水，服务既没按纯水算，也没提示两边矛盾，而是悄悄替他挑了质量浓度那一边。

第二条的请求体是这样的，打到 POST /v1/evaluate：
{"feed":{"molarity_mol_per_l":0,"mass_concentration_g_per_l":5,"molar_mass_g_per_mol":58.44,"temperature_k":298.15,"vanth_hoff_factor":2},"applied_pressure_bar":12,"feed_flow_lh":1000,"permeability_lmh_per_bar":1.8,"area_m2":36,"salt_rejection":1}

反方向也有一处。摩尔浓度给 0.1、质量浓度写 0、不给摩尔质量，服务照收不误按 0.1 算；同样不给摩尔质量、质量浓度改写成 5，它就回 400 说摩尔质量必须为正。都是「写了质量浓度却没配摩尔质量」，只因为数值是 0 就被当成没写。

登记档那条路上也一样。把上面摩尔浓度为 0 的那份加个 name，用 POST /v1/cases 登记，能登记成功；接着 GET 这份档，返回的 feed 里摩尔浓度那一项没了，和当初交上去的内容不一致；再点名核算，拿到的还是 0.0856 那套数。表单是拿 GET 回来的内容回填页面的，用户看到自己填的 0 凭空消失，只会更糊涂。

我要的效果是：请求里「写了 0」和「压根没写」必须区分开。摩尔浓度显式给 0，同时又给了非零质量浓度和摩尔质量，要和 0.05 那条一样回 400、inconsistent_concentration，原因里带上两边的数值；质量浓度只要显式出现，哪怕是 0，缺摩尔质量时就得跟写 5 的时候一样被拦下。临时核算和点名登记档核算，对同一份内容必须给出同一个判定，不能一个拒、一个算出结果。登记成功的档 GET 回来，字段要跟提交时对得上，显式给的 0 要原样出现在返回里。

有几样行为得保持现状：只带摩尔浓度 0、其余浓度项都不带，或者三项都带但摩尔浓度 0、质量浓度 0、摩尔质量为正，这两种纯水写法照旧按 0 mol/L 正常出结果；只给质量浓度配摩尔质量、只给摩尔浓度、两者自洽同时给，这三种写法算出来的数一位都不许变；内置苦咸水档点名核算还是约 4.24 bar 的渗透压。仓库里原有的用例眼下都是绿的，改完之后也得是绿的；上面三种出问题的组合（显式 0 撞上非零质量浓度、质量浓度写 0 却没摩尔质量、登记后再读回）每种都要有一条用例守着，往后谁再碰这块，跑一遍就能发现。
